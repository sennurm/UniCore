## Current State

UniCore is in the **requirements phase** — no source code or build tooling exists yet. Detailed module requirements live in `requirements/` (start with `requirements/00-overview.md`). Implementation begins only after the user approves those documents. Before implementing any feature, read the corresponding requirements doc; before making changes that would result in code, run the SME requirement clarification pass first.

## Engineering Rules (project-level)

- **API security (locked 25-07-2026):** every API endpoint requires a valid session token AND a role+scope permission check; deny by default. The auth gate is ASGI middleware in `backend/src/unicore/core/security.py` (public endpoints are an explicit allowlist); every non-public endpoint must declare `rbac.service.require_permission("<action>")`. No cross-user data leakage: DAOs filter by the caller's scope in the query, response schemas expose only audience-appropriate fields, and "own data" endpoints resolve the subject from the AuthContext — never a client-supplied id. `tests/test_security.py` fails CI if any route responds without a token. See backend/ARCHITECTURE.md.
- **Logging:** the logging-standard skill is mandatory for any code that logs or adds endpoints/DB/AI calls.
- **Module boundaries:** vertical slices under `src/unicore/modules/`; router→service→dao→models one-way; cross-module access service-to-service only (enforced by tests/test_architecture.py).

## Application Context (maintained by the SME clarifier)

### Field / Domain
University management system for a large Indian multi-campus university. Modules: authentication/authorization (own identity store, password + OTP), student onboarding (import-only from existing ERP; students carry two one-to-one ids — **SIF** issued at admission and used as the import join key, and **Enrollment No** issued later as the canonical identifier, unique university-wide and correctable with audit), central timetabling (labs, electives, combined classes), QR-based attendance with anti-fraud controls, faculty task management (hierarchical downward assignment; tasks carry School-scoped shared **tags** — free-form, assigner+assignee editable, School Incharge-curated with entity-semantic rename/merge/deactivate, inherited by bulk copies and recurrence cycles, no personal data in tag names), per-School configurable student promotion, a Department-owned subject catalogue whose offerings are Programme-bound or **university-wide for Open electives** (students self-select one subject per elective group per term, against a capacity enforced under a row lock), syllabus coverage tracking, question paper generation (bank + blueprint, AI-assisted, sealed until Exam Cell release), and a two-tier PA (email+tasks) client — draft-only AI for ~20 leadership roles, AI-free mail+tasks for the staff tier. Admissions, fees, and exam conduct/valuation are out of scope (external ERP/exam systems; answer-script evaluation confirmed out of scope 25-07-2026 — subject-mapped evaluator eligibility recorded for a possible future module).

### Users & Roles
Students (hold the **`student` role scoped to their Programme** — granted automatically by the ONB import that provisions them, sole per student, never Section-scoped because Sections are per-term and membership already lives in ONB; locked 31-07-2026); teaching staff in five grades (Professor, Associate Professor, Assistant Professor, Tutor, Assistant Teaching Staff — all "Faculty Member" tier; Tutors/ATS cannot author question-bank entries); HoDs; **School Incharges** (one per School — hold every School-scoped power: promotion config+ratification, calendar approval, kind taxonomy, tag curation, attendance-impact policy, School Admin designation); **Faculty Deans** (one per Faculty Division — FET, FMC, FHSS, FSC, FMS, FHS, Agri); **Dean Academic Affairs** (University-level, line manager of all Faculty Deans); Admin/office staff; Non-teaching support (Exam Cell led by the **Controller of Examination**, Timetable Cell — still the central timetable author, lab assistants); the full non-academic staff tree (Dean Research, Dean Student Welfare & Chief Proctor, Dean IQAC, Finance Officer, Dean Admin & R&A, PRO chains — accounts with minimal access: leave, tasks, tier-2 PA; **Alumni get no accounts**); **Pro-Chancellor** (restored 28-07-2026 from the university's leadership page — **not** singleton, two holders documented) and Chancellor (top-of-hierarchy singleton, terminal approver). Org/access source of truth: `requirements/sources/module_access_matrix.xlsx` (25-07-2026). **PA (email+tasks) is two-tier:** tier 1 "Access to AI" (~20 leadership roles) gets the full EML client with draft-only AI; tier 2 (HoDs, all teaching staff, most admin staff — ~2,000 users) gets email client + tasks with **no AI features**; students/security/canteen/alumni get no PA. **Reporting chain** (AUTH-configured, drives leave routing and task escalation): Class In-charge → HoD → School Incharge → Faculty Dean → Dean Academic Affairs → VC → Pro-Chancellor → Chancellor; Registrar → Pro-Chancellor. Principal is a School-level title ("equal to school incharge"), so Principals route as School Incharges — not a campus tier. Non-academic staff resolve to a **unit head** from the AUTH role registry (e.g., Exam Cell → Registrar); the registry also names who designates each auxiliary role (School Admin ← School Incharge, subject coordinator ← HoD, School exam coordinator ← Controller of Examination, HR designate ← Registrar, VC/Pro-VC office list ← Super Admin). Leave/escalation routing **cascades past levels that are on approved leave or vacant** (cause recorded per hop; Chancellor terminal; chronic vacancy alerts after a configurable 5 working days). Leave module (10-leave-management.md): single-approver routing with auto-cascade past approvers on leave and standing upward delegation; student leave types have School-configurable attendance impact (counts-as-present / absent / condonation-evidence); staff have simple per-type balances (accrual/LOP stays in external HR). Faculty leave/absence triggers **rebalancing**: ranked clash-free substitute suggestions to the HoD (never auto-assigned); faculty can also **swap** specific class occurrences by mutual consent (HoD notified, not a gate; occurrence-level only, one hop, no permanent swaps). **No parent/guardian or external-examiner access.** Authorization is RBAC with org-unit scoping over the hierarchy University → Faculty Division → School → Department → Program → Section. Terminology: "Faculty Division" = academic grouping; "Faculty Member" = teacher; "Class In-charge" = section owner (sole authority to correct captured attendance, with mandatory reason). Users hold multiple roles (an HoD may also be a Class In-charge), and leadership roles support **additional charge** — one person holding the same role at multiple org units (the org chart itself shows Faculty Division FMC held by Dean FET and FHS by Dean FMS) — under a strict **singleton rule**: at most one active HoD per Department / School Incharge per School / Faculty Dean per Faculty Division / Class In-charge per Section, changed only via atomic supersede (revoke + issue together). **Term-scoped assignments:** Class In-charge grants and faculty subject allocations (carried by the term's published timetable) are valid only for the current semester/year per the School; promotion ratification publishes a per-Section term-closure event that revokes these grants and archives the timetable; every new term requires fresh designation — nothing rolls over. **Sections are per-term instances** (Program × term × label, labels may repeat across terms) created by the Timetable Cell during term setup; org-unit CRUD above Section (Faculty Division/School/Department/Program) is Super Admin-owned, deactivate-never-delete. **Department is optional in the catalogue import** — most Schools have none, so blank department columns synthesise a default Department mirroring the School, flagged `auto_created`; Programmes carry level, duration, mode, category, industry partner, internship months and lateral-entry semester. Structure source of truth: `Takshashila_University_Schools_and_Programmes_Updated.docx` reviewed in `docs/reviews/org-structure-vs-university-document.md` (28-07-2026). Each School uploads a per-term **academic calendar** (start/end, exam-date ranges, special events; School office uploads, School Incharge approves, versioned) which also carries the term-archival backstop date; campus holidays stay with System Admin; exam/special-event dates drive soft warnings only. **Attendance freeze:** triggering a Program's promotion run freezes its attendance corrections; post-freeze corrections commit only via an open dispute (non-ratified students), retro counts-as-present leave marking stays exempt until ratification, and never-opened Periods resolve post-freeze by HoD write-off only.

### Regions
India, multiple campuses, 15,000+ students. All personal data resides in India-region infrastructure. IST timezone, DD-MM-YYYY dates, English UI (MVP). **Curriculum cadence is a mandatory School attribute set at creation** (semester | yearly), inherited by every Programme beneath it and overridable per Programme for genuinely mixed catalogues (PhD, D.Pharm) — locked 30-07-2026, superseding the earlier "cadence is a Programme attribute" wording. Each School owns its own promotion workflow.

### Reserved vocabulary (locked 30-07-2026)
**"Batch" means the admission cohort and nothing else** — (Programme × joining year), e.g. `BT-CSE-2026`, auto-created on first student import, named from a configurable university-level template. It previously carried three unrelated meanings; the others were renamed: TTM's lab partition of a Section is a **lab group**, ONB's CSV import execution is an **import run**. Docs are updated; **the code rename is still outstanding** (~68 backend, ~11 frontend sites). Other locked terms: **position** = a student's place in the ladder (semester *n* or year *n*; one number is authoritative, the other derived), **class-size cap** = max students per Section, School-configurable over a university default. Lateral entrants belong to the batch they will **graduate** with, not their literal joining year. A **detained** student keeps their original batch for records but is promoted by **position**, so promotion queries key on position, never on batch alone.

### Legal & Regulatory Constraints
- **DPDP Act 2023** — notice + versioned consent; separate explicit consent for attendance geolocation (only pass/fail proximity retained, never location traces); correction/erasure grievance flow (academic records carry statutory retention exemptions); breach notification duties.
- **No minors:** stakeholder decision (24-07-2026) — all students are 18+ at admission; the system carries **no** parental-consent machinery and **no** DOB age guard (DOB is imported but never age-checked). Residual risk accepted: if admission policy ever admits a minor, UniCore has no consent safeguard or signal.
- **UGC/AICTE norms** — minimum-attendance norms (commonly 75%) gate promotion/exam eligibility; thresholds must be School-configurable, never hardcoded.
- **No biometric data anywhere** — QR attendance was chosen partly to avoid it.
- India SMS/DLT regulations apply to OTP delivery.
